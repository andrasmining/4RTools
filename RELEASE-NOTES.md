# 4RTools Vanilla 0.6.9

This patch fixes multi-client recovery so two Vanilla clients can no longer fight over the foreground window, proxy list, username/password fields, server dialog, character screen, or resume hotkeys.

- Recovery is now globally **sequential** across managed clients. One account owns the recovery workflow from launcher start through GAME START, proxy selection, credential entry, server selection, character selection, confirmed gameplay and the one-shot Autobattle resume hotkey. Only after that client is Online may another account begin its recovery UI workflow.
- A healthy already-running client is left alone while another missing/disconnected client is recovered. If the current recovery attempt is waiting in exponential backoff, another due client may recover, but there is still never more than one active recovery/input workflow at a time.
- The cold-start test is now explicitly `TEST STARTUP (SEQUENTIAL)`. With two configured accounts it validates Client 1 end-to-end first and only then starts Client 2.
- Removed the artificial `TEST RESTART RECOVERY` button. The meaningful outage validation remains `ARM MANUAL NETWORK-DROP TEST`, which observes a real disconnect and waits for recovery back to Online.
- Once gameplay has previously been confirmed, a detected disconnect/logged-out modal or a return to Vanilla's login/service shell is treated as an outage. 4RTools closes only that affected Vanilla client and recovers it through the normal launcher path instead of trying to continue inside a stale/disconnected client.
- A Vanilla process that exits outright is also queued for the same full launcher recovery path.
- Failed unattended recovery attempts now use exponential backoff instead of retrying aggressively: 30 seconds, 1 minute, 2 minutes, 4 minutes, 8 minutes, and so on, capped at **one attempt per hour**. A confirmed successful return to gameplay resets the failure/backoff state.
- Launcher/login failures close the failed recovery client before entering backoff so stale windows cannot receive later credentials or selections.
- Recovery ownership is released safely when the supervisor is stopped, an account is disabled/removed from the active client limit, configuration is incomplete, or a recovery attempt fails. This prevents another account from being permanently blocked behind stale state.
- Existing visual recognition remains fail-closed. Proxy, username/password and server selection use the current Vanilla client image and recognized UI geometry rather than fixed desktop coordinates. Character selection remains client-relative/normalized and the resume hotkey is coordinate-independent.
- Recognition regression coverage includes multiple client resolutions plus softened/resampled rendering for proxy, login and server-dialog surfaces. If a required layout cannot be recognized confidently, no unverified click/credential input is sent.
- Persistent account configuration, DPAPI-protected passwords, per-startup/10 MB rotating logs, updater, launcher/TThorForm handling and the working one-client flow from 0.6.8 remain intact.

The sequential-recovery implementation and follow-up lease edge cases were each built, tested, packaged and portable-smoke-tested on Windows before being committed. The final release is also gated by the normal Windows build and Verified release pipelines. Real simultaneous two-client startup and real server/network outages still require local Vanilla/Gepard validation on the user's machines; CI cannot emulate the live game UI. No Gepard bypass, code injection, packet manipulation or game-memory writes are used.
